## 内容摘要

文章把问题放在“Agent 写入真实数据库”场景，主张最危险的风险不是模型幻觉，而是一次用户确认导致多次写操作。它讨论了以下链路和工程约束：

- 模型只能提出写操作，不能自行批准写操作。
- 用户确认的必须是服务端 `prepareArgs` 归一化、校验后的具体参数。
- 同一确认卡只能被一个请求原子认领，避免 GET 后再 DELETE 的竞争窗口。
- Tool 只做受控适配，真实写入复用业务 Service。
- 没有可信成功回执时，模型不能声称“已完成”。
- 写操作确认状态和最终回复生成使用两套状态机，成功回执激活续答；回复重试不重新开放写工具。
- `commit()` 后连接中断属于 outcome unknown，不能直接据此重跑写操作。
- Redis 适合短生命周期确认和执行状态，但不应成为长期业务事实的唯一来源。
- 文章还覆盖能力注册表、Tool Policy、确认令牌绑定、TTL、边界测试和工程代价。

## 对现有框架的增补建议

1. 在 U02 后加入一个小转折：**模型提出 Tool Call，不等于服务端允许执行**。这能承接“Agent 不是唯一重试来源”，也避免学员把安全问题归咎于提示词。
2. 在 U05 增加一张“确认状态”简图：`ready → running → settled`，第二次请求只能读取 `running/settled`，不能再次进入业务 Service。
3. 在 U05 或 U06 增加“写阶段与回复阶段分离”：可信写回执生成后，回复可重试，但回复阶段不再开放写工具。
4. 将“参数准备后的确认”作为幂等前置条件：确认对象应绑定稳定业务操作、规范化参数和执行主体；不要求样章讲完整鉴权实现。
5. 把 `commit` 后连接中断作为一个精确例子，明确它是“结果未知”，而不是“事务一定回滚”；这一点适合放入 U03 的危险窗口 C。
6. 把文章的测试矩阵浓缩成一页迁移练习，验证学员是否关注状态转换和执行顺序，而非只看 HTTP 200。

## 配图风格分析

文章使用 4 张主要信息图，整体特征是：

- 冷灰或近白背景，蓝紫色为主色，绿色表达成功，橙色表达风险，红色表达失败。
- 圆角矩形、彩色竖条、胶囊标签、轻阴影和大量水平/垂直连线。
- 文字较多，像架构评审图或 SaaS 产品技术方案图；信息密度高，适合工程师快速扫描。
- 图 1 用“确认一次”到多个重复执行入口说明问题；图 2 用三层架构展示 Planner、服务端控制层和业务事实层；图 3 展示 Confirmation 与 Continuation 两套状态机；图 4 以测试矩阵承载不变量。
- 图片中英文术语和代码名较多，如 `confirmationToken`、`prepareArgs`、`Atomic Claim`、`Trusted Receipt`、`Continuation`，工程感强，但对未接触该实现的学员需要配讲解。

## 对 CDL 视觉系统的建议

采用“章节角色化 + 原理图蓝图化”的双层视觉：

- 暖色手绘机器人只承担问题、情绪和场景转折，例如拿着两张订单、等待回执、看到 `unknown` 后犹豫。
- 技术机制图使用文章这类蓝调架构图的优点，但降低卡片数量和文字密度，保持每页一个机制结论。
- 状态、证据和副作用继续使用固定语义色：蓝色表示调用/证据，绿色表示已确认成功，橙色表示处理中或风险，红色表示失败或禁止。
- 可以借鉴文章的圆角模块、胶囊标签和状态机结构，但不要把整套页面做成统一 SaaS 仪表板；角色页和技术页之间需要有明显节奏变化。
- 页面底部用一句可验证的结论收束，例如“没有成功回执，只能说结果未知”，不要使用装饰性口号。

## 教学结论

这篇文章不是当前课程的替代大纲，而是一个很有价值的“工程实现深化方向”。它证明当前主线可以自然延伸到：确认授权、原子认领、业务 Service、可信回执和续答隔离。建议框架评审时把其中 4 个概念列为主线必讲：

1. 模型提出不等于服务端授权。
2. 同一业务意图需要稳定操作身份。
3. 执行状态需要原子认领和可查询结果。
4. 写操作回执与最终语言回复必须分离。

其余能力注册表、参数哈希、Redis Key 脱敏、TTL 细节和完整测试矩阵放入扩展资料或 Demo。
