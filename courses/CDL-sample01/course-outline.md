- 建议标题：让 Agent 安全地重试：一次工具调用为什么变成两次执行？
- 学员：1～3 年软件研发或算法开发经验；HTTP、异常处理基础暂按需短回顾，尚无实际学员验证。
- 预计纯阅读：35 分钟；思考与作答另计约 5～8 分钟。视频、Demo 未启用，不计入该预算。所有时长待实际走查验证。
- 课件规模：暂估 20～24 页，按样章阅读密度调整。
- 核心问题：工具结果未知时，Agent 如何决定下一步，避免把一次业务意图变成两次业务执行？

## 教学路径比较

| 路径 | 优点 | 主要限制 |
| --- | --- | --- |
| 事故调查 → 机制还原 → 决策与修复（推荐） | 先产生问题，沿同一案例逐层解释，便于建立因果理解 | 需控制事故细节，避免挤占机制讲解 |
| 超时、重试、幂等概念 → Agent 应用 | 术语结构规整，适合已有分布式系统基础的学员 | 容易成为概念清单，Agent 特有问题出现较晚 |

推荐以“同一笔订单为什么出现两张订单”为主线，邮件与服务重启只作为迁移场景，全课最多使用三个业务场景。均为构造教学案例，不宣称真实事故。

## 能力目标与理解证据

1. 区分明确未执行、执行中、已成功、结果未知：能对调用时间线标出系统实际状态与 Agent 所知状态。
2. 解释重复执行的因果链：能指出效果发生、回执接收与本地持久化之间的风险窗口，以及 Agent 与普通客户端重试的区别。
3. 选择有边界的处理方案：给定工具契约与调用记录，能决定查询、使用原业务操作标识重试、等待、升级人工或停止，并解释方案限制。

## 章节结构

### U01 一次请求，两张订单：先看到用户损失（3 分钟）

- 用户让 Agent 预订一次行程，界面显示超时，稍后发现生成两张订单。损失包括重复支出、取消成本及信任下降。
- 先展示用户视角，不立即揭示全部内部过程。
- 开场提问：界面没有显示成功，能否证明服务没有执行？
- 视觉：简化机器人拿着两张相同订单；角色作为 Agent，订单服务画成独立模块。
- 转折：问题不只是“模型没记住”，还涉及外部执行与结果证据。

### U02 回放一次工具调用：执行与知道执行是两件事（5 分钟）

- 最小链路：Agent 决定调用 → 执行器发出请求 → 外部服务产生效果 → 回执返回 → Agent 接收并持久化结果。
- 对照普通 HTTP 重试：没有 Agent 也可能重复执行；Agent 额外存在重新规划、重新生成参数与任务恢复入口。
- 分开两条时间线：外部实际发生了什么；Agent 持有什么证据。
- 解释明确失败与结果未知；“失败响应”需结合工具契约判断是否保证未产生效果，不能仅看报错或状态码。
- 图示 F01：执行线与证据线；标注“订单已生成，但 Agent 尚不知情”。

### U03 三个危险窗口：为什么会失去完成证据（6 分钟）

- A：请求发出后 Agent 被杀死或用户终止；外部操作可能继续，取消请求也未必确认成功。
- B：组合工具执行到一半，例如创建订单成功但通知步骤失败；整体报错不能抹去前半段效果。
- C：业务成功后回执丢失、接收超时，或接收后尚未持久化就崩溃。
- 恢复后如果将“缺少成功记录”误当“未执行”，就可能再次调用。
- 因果链：缺少可靠完成证据 → 误判可重试 → 再次请求 → 缺少有效识别和去重 → 重复业务效果。
- 补充边界：重复请求不必然产生重复效果；模型主动重复规划也是入口之一，并非本课核心故障链的全部解释。
- 小判断：标出三个窗口中哪些能证明业务未发生。

### U04 谁在重试：为什么只改提示词不够（4 分钟）

- 可能发起重试的层次：客户端或 SDK、工具执行器、模型重新决策、任务恢复逻辑。
- 多层策略叠加可能放大尝试次数；区分重试同一操作与重新发起一笔业务。
- 原则：明确重试责任、共享业务操作身份、统一尝试预算；避免各层互不知情。
- 区分单次工具调用标识与业务操作标识：重新生成调用不应自动意味着新的业务意图。
- 转折：提示词能影响决策，但业务服务是否重复产生效果仍需要工程约束。

### U05 安全重试需要什么：同一操作身份与有效幂等（7 分钟）

- 基线：超时后直接再调用为何不足；只在本地记一笔也无法覆盖所有崩溃窗口。
- 围绕一笔业务意图保留稳定 operation_id，在重试与恢复时复用；真实的新业务意图应使用新标识。
- 服务端在有效范围内识别同一操作，检查参数一致性，并维护执行状态或返回既有结果。
- 强调并发竞争：“先查没有、再执行”存在竞争窗口；需要原子认领、唯一约束等机制，且须分析与业务效果的关联。
- 用两次相同请求的时间线和少量伪代码表达原理，不绑定 Agent 框架。
- 边界：去重范围与有效期、处理中状态、参数变化、外部服务不支持幂等、跨系统副作用；幂等键并非全局 exactly-once 保证。
- 不引入完整分布式事务实现，避免范围失控。

### U06 结果未知时，Agent 下一步怎么做（6 分钟）

- 先读工具契约：是否有副作用，能否查状态，是否支持可靠幂等，是否有明确的未执行证据。
- 已成功：使用已确认结果；处理中：查询或有界等待，不另起一笔；明确未执行且错误可重试：按预算重试。
- 结果未知：优先用业务操作标识查状态；具备有效幂等保证时可按契约使用原标识重试；否则保留未知状态并升级处理。
- 人工确认需呈现已有证据和潜在重复效果，不能把“确认重试”包装成保证安全。
- 组合工具逐步记录和恢复，已完成步骤避免盲目重放；撤销或补偿是额外业务动作，可能失败。
- 用户停止后，说明哪些已完成、哪些未知及取消是否被确认；不把本地停止当作外部撤销。
- 图示 F02：带状态证据与工具能力条件的决策树；说明查询和等待也需预算。

### U07 回到事故：修复与迁移验证（4 分钟）

- 对照原始事故，逐项标出稳定业务标识、状态查询、服务端幂等及恢复记录各解决哪个窗口。
- 综合任务：订单请求超时，Agent 重启，本地没有成功记录；提供两种不同工具契约，让学员选择下一步并说明证据和限制。
- 迁移一：报价邮件重复发送，既可能打扰客户，也可能出现不一致报价；无可靠去重能力时不能照搬订单方案。
- 迁移二：服务已恢复后被再次重启，重复效果可能造成二次中断；检查目标状态与并发变化，不能凭“看起来幂等”断言安全。
- 收束：缺少成功证据不等于没有执行；安全重试取决于可核验状态、稳定操作身份与执行端能力。

- 机器人采用用户提供图片为候选原型，尚未定稿；建议简化结构并补足夹爪手臂。
