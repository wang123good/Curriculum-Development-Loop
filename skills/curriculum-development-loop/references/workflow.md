# 工作流与评审依据

## 1. 选题定位

定位卡包括：学员背景、实际工程问题、可观察的能力目标、前置知识、承接课程、后续课程、本课必讲与排除范围、时间预算。细化学员岗位及所需前置能力，例如 Python、异步调用、检索或概率基础，标记已掌握、需回顾、需补充及未知；未知基础不当作已具备。没有真实学员数据时将能力缺口写为待验证假设。

用代表性、工作相关性、可迁移性筛选内容；区分必须掌握、工作时查阅、扩展阅读和后续课程内容。不要用固定概念数量代替范围判断。

通过条件：课程负责人认可题目大小、学习收益及课程衔接。

## 2. 框架设计

提出少量有实质区别的方案，比较开场问题、贯穿案例、概念依赖、认知转折、章节时间与结尾迁移问题。用“目标—理解证据—教学内容”检查每个目标是否有支撑。

根据学员已有经验判断哪些知识正式讲、简短回顾或默认掌握。认知层级服务实际任务，不强制每课覆盖所有层级。

通过条件：课程负责人确认教学路径、技术深度与可选交付物。此阶段仅做必要查证，系统调研在框架通过后进行。

## 3. 调研

优先原始论文、官方文档、可核验实现及可靠工程案例。记录论断、链接、发布日期或技术版本、核实日期、对应章节、限制和冲突。原创教学案例明确标为构造案例，不冒充真实项目。

充分性标准：核心机制有依据、关键概念有例子、方案取舍有支撑，未决问题已披露。资料不足时补充调研或缩小论断，不编造事实填充内容。

## 4. 教学样章

选择核心且能暴露理解难度的小节，提供页面、图解、讲稿及理解问题。用具体实例 → 中间图示 → 抽象机制建立理解；给出必要推导、对照或反例，说明可迁移原理。

通过条件：课程负责人认可解释深度、案例、话术、视觉和密度，再展开全课。

## 5. 内容与媒体

每小节检查目标、概念、解释、示例、取舍和理解验证是否充分，避免机械套用固定页数或例子数量。术语在首次实质使用时解释，检查图示和案例中的隐藏术语。

按教学用途选择媒体：结构与比较用静态图，过程与状态变化考虑动画，真实运行行为考虑 Demo。网页、PDF、视频、Demo 分别记录启用状态、目标、范围、预计用时和验收方式；未启用项不阻塞交付。

风格先以样页确认，可跨课程变化，也可按章节调整，但保持信息层级和语义一致。

## 6. 阅读走查与试讲

分别记录预计阅读时间、实际阅读观察和现场试讲时间。定位时明确 30～40 分钟是纯阅读还是完整核心学习时间；分别记录思考、视频、Demo 操作与等待，扩展另计。未确认口径时暂按纯阅读估算。没有目标学员实测时标记估算，不宣称已验证时长。

试讲检查：开场是否形成有效问题、过渡是否自然、概念是否跳跃、例子是否解释因果、话术是否吸引人、信息密度是否合适。设置少量预测、解释或方案判断问题，答案后置；完整练习及考核按需选择。

真实反馈和 AI 模拟反馈分别标注，模拟不能替代真实学员验证。评审意见记录具体页面或讲稿段落、问题、影响、建议与复核结果。

## 7. 修订与验收

结构问题返回框架，证据问题返回调研，表达问题返回内容或视觉开发。修改后复查所有受影响载体；关键机制或教学顺序变化时重做相关试讲。

验收包括技术准确、目标覆盖、课程衔接、时长记录、可读性、讲稿可用性以及已选附件的实际可用性。

## 8. 长任务与流程迭代

进度记录保留当前阶段、已确认决定、待办、阻塞、交付物位置和下一监督点。评审状态区分待评审、通过、需修改、暂缓，未收到答复不算通过。

变更区分单页修改、单课偏好和长期流程规则。记录原因、适用范围、影响产物及用户确认状态，避免在长任务中丢失要求。同步 GitHub 采用明确的提交与推送；持续自动同步需要另行配置，不能仅凭一次创建仓库就宣称已启用。
